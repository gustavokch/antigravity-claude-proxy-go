# Codex Gateway Wire Identity and its Exception to the Empty `tls.Config` Rule

## Context

The Codex gateway serves Anthropic `/v1/messages` requests from a pool of ChatGPT-subscription accounts through the Codex backend, `https://chatgpt.com/backend-api/codex/responses`. That backend is the one the official Codex CLI calls. Each request authenticates with the account's OAuth access token and names the account in `Chatgpt-Account-Id`, so what the request says about its client is seen alongside a real subscription credential.

The reference implementation is CLIProxyAPI (MIT, `router-for-me/CLIProxyAPI` at `681ce41`), which already serves Claude-format clients from this backend. It sends every Codex request with the `codex-tui` `User-Agent` and `Originator` of the Rust CLI's terminal UI, and dials `chatgpt.com` with utls `HelloChrome_Auto`, a Chrome ClientHello. Its code gives "providers that require browser-like TLS" as the reason, and its Codex path mentions Cloudflare 1010 blocks.

AGENTS.md says to use Go's default `crypto/tls` handshake, and where a gateway must look like a client Go cannot imitate, to replay that client's recorded hello (ADR-0004). Neither choice fits Codex cleanly. The real client is a Rust program, and this repo has no capture of its handshake. Go's default hello with `codex-tui` headers is a contradiction: the TLS layer says Go while the headers say the Rust CLI. A Chrome hello with the same headers is a contradiction too, since the TLS layer then says Chrome. Without a capture, every option sends a handshake the real client does not.

On 2026-11-08 the Chrome hello was chosen anyway, for parity with a proven implementation. CLIProxyAPI's pairing of a Chrome hello and `codex-tui` headers is known to be accepted by this backend. A Go default hello paired with the same headers has never been sent to it.

## Decision

The "empty `tls.Config`" rule in AGENTS.md remains authoritative. It gets one more scoped exception, beside Zen's and Claude Code's, as follows.

1. **Scoped Boundary**: the exception covers only requests to `codex.baseUrl` (default `https://chatgpt.com/backend-api/codex`): `POST {base}/responses` and `GET {base}/models?client_version=0.154.0`. The OAuth calls to `auth.openai.com` (token exchange and refresh) use `transport.Upstream()` and Go's default handshake.

2. **TLS**: `internal/transport/codex.go` (`transport.Codex()`) dials with utls `HelloChrome_Auto`. This is the utls library's maintained Chrome profile, not a hello built by hand in this repo, so it changes when the utls version in `go.mod` changes rather than when a capture is refreshed. The transport pools HTTP/2 connections when ALPN selects `h2` and falls back to HTTP/1.1 otherwise. It dials `HTTPS_PROXY` or `ALL_PROXY` itself through `internal/proxydial`, for the reason ADR-0004 gives: net/http ignores a custom TLS dialer behind a proxy and would send Go's handshake over the tunnel instead. The response-header timeout is the one `transport.Upstream()` uses.

3. **Header set**: `codex.Client.Send` builds every request from its own fields, and no client header passes through. It sends `Content-Type: application/json`, `Authorization: Bearer <token>`, `Accept: text/event-stream`, `User-Agent`, `Originator`, `Chatgpt-Account-Id`, `Session-Id` (the prompt cache key, when there is one) and `X-Codex-Routing-Hint: model=<model>[;tier=<tier>]`. The model fetch sends `Accept: application/json` with the same identity headers. The defaults are CLIProxyAPI's: `User-Agent: codex-tui/0.154.0 (Mac OS 26.5.2; arm64) iTerm.app/3.6.11 (codex-tui; 0.154.0)` and `Originator: codex-tui` (`codex.DefaultUserAgent`, `codex.DefaultOriginator`).

4. **Identity overrides**: `codex.identity.userAgent` and `codex.identity.originator` replace the two defaults when set. `IdentityConfig.Validate` rejects control characters, because both values become header values. An empty field keeps the default.

5. **Body**: every request carries `"store": false` and `"include": ["reasoning.encrypted_content"]`, as CLIProxyAPI's do. With `store:false` the backend keeps no conversation state, and the proxy sends the whole conversation each turn. Reasoning survives between turns only as the opaque `encrypted_content`, which travels in the Anthropic thinking block's `signature`: a reasoning item's `encrypted_content` becomes the `signature` on the way down, and an assistant thinking block whose signature starts with `gAAAA` (a Fernet token) goes back up as `{"type":"reasoning","summary":[],"content":null,"encrypted_content":<signature>}`. The thinking text itself is never sent. A signature that does not start with `gAAAA` belongs to another backend (Anthropic or Gemini, in a conversation that changed gateways) and is dropped. There is no proxy-side replay cache, unlike CLIProxyAPI: the client already carries the signature, so the conversation is the cache. `temperature`, `top_p`, `top_k`, `stop_sequences`, `metadata` and `previous_response_id` are never sent.

   When the backend refuses a replayed signature, answering 400 `invalid_encrypted_content`, the proxy sends the request once more on the same account without the conversation's reasoning items. The cause is not confirmed; the likely triggers are a session that moved to an account in another workspace, or a model switch. That one turn loses the model's earlier reasoning. The client still holds the refused signature, so the conversation's later turns carry it again and each pays the same 400 and resend.

6. **No client-drift pinning**: `scripts/client_drift.py` does not track the Codex CLI. `codex.DefaultUserAgent` and `codex.DefaultClientVersion` (`0.154.0`, also the `client_version` of the model fetch) are hand-edited constants copied from CLIProxyAPI. They go stale as the Codex CLI releases, and someone has to bump them by hand. Until then an operator can override the headers through `codex.identity`.

## Consequences

- The TLS layer says Chrome while the headers say the Rust CLI. A check that compares the two sees the mismatch. This decision accepts it because it is the mismatch CLIProxyAPI already sends. If the backend starts rejecting it, the fix is the ADR-0004 route: capture the real Codex CLI's hello and replay it through `internal/tlsreplay`.
- The Cloud Code path is untouched and keeps Go's default handshake. Requests to any host other than `codex.baseUrl` keep it too, the Codex OAuth calls included.
- Codex refresh tokens rotate on every refresh and are single-use: OpenAI's token endpoint answers a reused one with `refresh_token_reused`. If the proxy and the codex CLI shared one, whichever refreshed second would be signed out. That is why `~/.codex/auth.json` is not imported, and accounts come only from the WebUI OAuth login. For the same reason, the rotated tokens are written to `config.json` before the new access token is used, so a crash cannot lose the only valid refresh token. A refresh error that says the grant is gone marks the account `needs_login`.
- Go adds `Accept-Encoding: gzip` itself. `Send` sets no `Accept-Encoding`, so the HTTP transport adds `gzip` and decodes the response before the proxy reads it. CLIProxyAPI sends `gzip, deflate, br, zstd`, and the real CLI's value has not been captured, so this header differs from the reference.
- The Codex catalog marks every model `prefer_websockets`. This gateway, like CLIProxyAPI for Claude-format clients, speaks plain HTTP only, so its requests do not take the transport the catalog prefers.
- Usage windows come from the `x-codex-*` headers of responses the gateway already receives. No usage endpoint is polled, so the gateway sends no request kinds beyond the two in §1.
- The reference itself is not consistent: CLIProxyAPI's model-fetch tool sends `codex_cli_rs/0.159.0` with `Originator: codex_cli_rs`, while its executor sends `codex-tui/0.154.0`. This gateway uses the executor's pair for both calls.
