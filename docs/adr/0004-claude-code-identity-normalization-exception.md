# Claude Code Wire Identity Normalization and its Exception to ADR-0001

## Context

ADR-0001 states that custom endpoints are forwarded transparently, streaming "the client request and server response without altering the body payload". ADR-0003 §2 restates that as the Main Route Invariant: general user requests directed through `customEndpoints` continue to use pure, transparent `httputil.ReverseProxy` without payload alteration.

Anthropic distinguishes first-party Claude Code traffic from third-party traffic by fingerprint, not only by credential. A request forwarded verbatim from a foreign harness (Cursor, an OpenAI shim, any SDK) advertises that harness through its headers and through body fields Claude Code never sends. Forwarding it unaltered to an Anthropic-shaped endpoint is what the fingerprint check is looking for.

`internal/ccidentity` therefore rewrites the request to match the captured first-party traffic, currently `.reference/client-drift/claude.jsonl`, which `scripts/client_drift.py` re-records when the installed Claude Code changes (`ccidentity.ClientVersion` names its version). The 2.1.304 captures `.reference/claude-code-headers-20261020*.jsonl` and the 2.1.280 captures `.reference/claude-code-headers-20260923*.jsonl` stay as history. `internal/api/server.go` calls `ccidentity.ApplyBody` on the custom-endpoint path — the exact path ADR-0001 and ADR-0003 §2 declare untouched. That is payload alteration on the main route, so it is recorded here rather than left as a silent override.

## Decision

ADR-0001 remains authoritative. Its payload-alteration guarantee is narrowed by one exception, scoped as follows.

1. **Scoped Boundary**: normalization applies only when the endpoint is Anthropic-shaped (`isAnthropicEndpoint`: a URL path ending in `/messages`, or a host under `anthropic.com`), and only when the endpoint carries no configured `apiKey`. Any other custom endpoint is forwarded exactly as ADR-0001 describes.

2. **Payload Alteration Performed**: within that scope, `ApplyBody` makes three changes to what the request says, and writes the whole body again around them (see the last paragraph of this item).
   - `metadata.user_id` is set to the captured stringified JSON object (`device_id`, `account_uuid`, `session_id`, in that order). Other `metadata` keys are preserved.
   - A system block carrying the `x-anthropic-billing-header` line is prepended to `system`. The caller's own system prompt is preserved after it. The line's `cc_prompt_id` and `cc_turn_index`, and the `x-claude-code-prompt-id` header, follow the user prompts in the request's own `messages` (`ccidentity.TurnOf`): a tool follow-up repeats its prompt's values and the next prompt gets new ones. Nothing is stored between requests for these, so a retry or a cache-bump replay of the same body sends the same values. `cc_prev_req` names the request whose reply the latest assistant message echoes, as the real client reads it from its transcript. Its one piece of state, `ccidentity.ReplyLog`, maps each normalized reply to its `request-id` per account (or endpoint) and session, so a replay of the same body names the same request too.
   - Six top-level fields the captured traffic never carries are deleted: `temperature`, `top_p`, `top_k`, `stop_sequences`, `tool_choice`, `service_tier`.

   Messages, tools, model and `max_tokens` keep their values. `context_management`, `diagnostics` and `output_config` are deliberately not synthesised: the capture shows Claude Code sending them, and this package cannot invent their contents.

   The body is re-encoded as a whole, because `cch` is a hash of the exact bytes sent (see Consequences). Top-level keys are written in the captured order, `model` first, followed by any key the capture does not show in the caller's own order. A value `ApplyBody` does not rewrite is the caller's own bytes, compacted: whitespace is gone, and nested key order and string escapes are the caller's. A value it writes is encoded without HTML escaping, as `JSON.stringify` does, where Go would turn `<` into `\u003c`. `cch` is computed last, over the bytes that go on the wire. A caller that compares the forwarded body with the one it sent sees the key order and the whitespace change, and the three changes above.

3. **Credential Invariant**: an endpoint with a configured `apiKey` is never normalized. `x-api-key` is on the header omit list, so normalizing such an endpoint would delete the credential it authenticates with; and the normalized request claims an OAuth Claude Code identity that an API-key credential contradicts. `internal/claudecode/client.go` applies the same refusal on the pooled gateway path.

4. **Fail Closed**: normalization runs before the reverse proxy is constructed, because `ApplyBody` can fail and `httputil.ReverseProxy`'s `Rewrite` hook has no error return. A body that cannot be normalized yields 502; it is not forwarded unaltered. An unnormalized body is the fingerprint this feature exists to remove, so forwarding it is worse than refusing.

5. **Opt-out**: `identity.disabled` on the endpoint (or on the Claude Code config for the pooled path) restores ADR-0001 behaviour exactly. The flag is a *disable*, so the zero value normalizes; an operator who wants transparent forwarding for an Anthropic-shaped keyless endpoint must set it.

6. **Advisor Beta Exception**: the captured beta list replaces the client's `anthropic-beta`, so a client beta not in the capture is dropped. `advisor-tool-2026-03-01` is the one exception, on both normalized paths. When the client's `anthropic-beta` names it, `ccidentity.Profile.WithClientBetas` returns a new list with the beta inserted right before `thinking-token-count-2026-05-13` (`advisorBetaPrecedes`), which is where Claude Code sends it. `claudecode.Client.SendMessage` (pooled gateway) and the custom-endpoint `Rewrite` in `internal/api/server.go` both call it before `ApplyHeaders`. The shared slice is never written. A client that does not send the beta gets the captured list unchanged, and a captured list that already carries it is not extended.
   - **Position, from the 2.1.311 bundle**: the client builds the list as `wt=jEn(model)`, then `if(LBt()&&(QC()||advisorModel!==void 0))wt.push(advisor)`, then `if(…&&!wt.includes(thinkingTokenCount))wt.push(thinkingTokenCount)`. The header is `c$(…)`, which keeps insertion order and does not sort. `jEn` returns the model's base list, which in the capture ends at `mid-conversation-tool-changes-2026-07-01`. `advanced-tool-use` and `mid-conversation-system-clear-at`, pushed later in the same function, follow `thinking-token-count` in the capture in push order. A client with the advisor on therefore sends the beta 8th of 15. `TestDefaultProfilePinsTheCapturedPathAndBetas` fails when a recapture drops `advisorBetaPrecedes`, because the position must then be read from the client again. The drift capture never turns the advisor on, so `scripts/client_drift.py` reads the beta's name from the installed binary (`claude.advisor_beta`). A new name moves the pin and is also a manual item.
   - **When the real client sends it**: `LBt()` allows the beta only on the first-party provider, the one OAuth requests use, and not when `CLAUDE_CODE_DISABLE_ADVISOR_TOOL` is set. `QC()` is the `tengu_sage_compass2` flag or `CLAUDE_CODE_ENABLE_EXPERIMENTAL_ADVISOR_TOOL`. So Claude Code sends the beta on OAuth requests whenever the advisor is enabled or an advisor model is set, including requests whose body carries no advisor tool. No live call has been made through this proxy with it. If OAuth rejected it, a request that carries it would fail where it previously went out with the beta stripped.
   - The identity gate does not exercise this case. Its baseline is a capture with no advisor request, and `scripts/verify-claude-code-identity.sh` sends a foreign beta, not this one. The position and matching rules are proved by `TestWithClientBetas`, and each path by `TestClient_SendMessage_NormalizedKeepsTheClientsAdvisorBeta` and `TestCustomEndpoint_NormalizedKeepsTheClientsAdvisorBeta`.

7. **count_tokens**: `POST /v1/messages/count_tokens` is normalized on the same two paths and under the same scope (§1, §3, §5), with the identity Claude Code sends on its own counts (`.reference/claude-code-count-tokens-20261107.jsonl`, 2.1.311 `/context`), not the messages one: `x-claude-code-request-class: auxiliary`, no `X-Stainless-Timeout`, no `x-claude-code-prompt-id`, and the five-entry list `ccidentity.CountTokensBetas`. That list is pinned in `scripts/client_drift.py` as `claude.count_tokens_betas`; the drift run never reaches `/context`, so it moves only with a recapture. The advisor beta exception (§6) does not apply: the count capture is the specification and carries none. The body is not normalized: the real count body carries `messages`, `model` and `tools` only, with no billing block and no `metadata`, so there is nothing to add and no `cch` to sign; the gateway writes only its model id into the client's bytes. Count answers carry no `anthropic-ratelimit-unified-*` headers, so the pool's rate-limit state is not read from them; a `429` still cools the account down.

## Consequences

- Foreign harnesses reach Anthropic-shaped endpoints without advertising themselves, which is the feature's purpose.
- ADR-0001's guarantee no longer holds unconditionally for `customEndpoints`. It holds for every endpoint outside the scope in §1, and for any endpoint with `identity.disabled`.
- Six request fields are silently dropped in scope. A caller that depends on `temperature` reaching an Anthropic-shaped endpoint must disable normalization for it.
- The capture is the specification. `scripts/diff_claude_code_identity.py` gates the produced request against the committed JSONL, so a drift from the captured shape is a test failure rather than a wire surprise. The gate cannot see Claude Code itself change: a new client version needs a fresh capture and a new baseline, as 2.1.304 did (new beta list, new `x-claude-code-prompt-id` header, new billing-line fields).
- Normalized requests leave over HTTP/1.1 with the TLS handshake of the real client. Claude Code runs on Bun, which has two TLS stacks: `fetch` (ALPN `http/1.1`) sends `/v1/messages` and `/api/eval/*`, and `node:https` (no ALPN) sends every `GET /api/claude_code/*`, the bootstrap, registry and settings calls. Go's `crypto/tls` cannot produce either BoringSSL hello, so the proxy replays the two recorded ClientHellos through utls (`internal/tlsreplay`; hellos and constructors in `internal/transport`: `ClaudeCodeMessages` for messages and `customEndpointIdentityTransport`, `ClaudeCodeDiscovery` for the account, model and OAuth calls). This is a second scoped exception to the "empty `tls.Config`" rule in AGENTS.md, beside Zen's: the Cloud Code path is untouched and keeps the default handshake. `.reference/claude-code-tls-20261020.json` holds the JA4 and JA3 of each stack as the real client presented them, and `scripts/verify-claude-code-identity.sh` fails when any phase presents another. The request-to-stack map is a capture of api.anthropic.com only; routing the OAuth calls (a different host) to the `node` stack is an inference. A Claude Code release that upgrades Bun changes both hellos and needs a recapture (`MITM_DUMP_HELLO_DIR` makes the capture addon save them). Requests forwarded unnormalized keep the shared transport and its h2.
- The replay dials the proxy itself when one is set for an https target: net/http ignores a custom TLS dialer for an https target behind a proxy and runs crypto/tls over the CONNECT tunnel, so the captured hello would silently never be sent. `http://`, `https://` and `socks5://` proxies are supported (`internal/proxydial`), and the CONNECT exchange is bounded by the request's context; another scheme is an error, not a bypass. A plain-http request goes through the proxy in absolute form.
- `cch` and the `cc_version` suffix are the hashes Claude Code derives, not random values: `cch` is the 20-bit xxHash64 (seed `0x4d659218e32a3268`) of the exact body bytes with the `model` value emptied and `max_tokens` removed, and the suffix is a salted SHA-256 of three characters of the conversation's first prompt. Both reproduce every body captured from 2.1.304, so `ApplyBody` writes the body the way the client does (captured key order with `model` first, the caller's values as its own compacted bytes, no HTML escaping) and signs it last. The gate checks both against the real derivation.
- The request is written the way the real client writes it, by `internal/httpwire` rather than net/http, which writes `Host` and `User-Agent` first, sorts the rest and cannot be told otherwise. The fetch stack writes its headers bytewise-sorted, then `Connection: keep-alive`, `Host`, `Accept-Encoding: gzip, deflate, br, zstd` and `Content-Length`; the node stack writes its own headers, then `Accept-Encoding: gzip, compress, deflate, br`, `Host` and `Connection: close`, one connection per request. The transport decodes gzip, deflate, br and zstd, as net/http does for gzip, and presents the body as decoded. This replaces the earlier decision to leave Go's `Accept-Encoding` alone. The node stack's header order is that of the captured `settings` request, and the position of `Content-Length` on a node POST is an inference; neither is known for the call sites the proxy has that the real client lacks. `scripts/diff_claude_code_identity.py` compares the order, and the Accept-Encoding and Connection values, instead of exempting them.
- `X-Stainless-OS` and `X-Stainless-Arch` default to the machine the proxy runs on, in the Stainless SDK's spelling (`MacOS`, `x64`), where they used to be the capture's container (`Linux`, `arm64`). The TCP/IP fingerprint of the connection names the real OS whatever the headers say, so a default that claims another is a contradiction. `identity.stainlessOs` and `identity.stainlessArch` override it for a proxy deliberately run behind another host's network identity. The gate compares the headers with the host it runs on.
