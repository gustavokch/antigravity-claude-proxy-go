anthropic-beta is conditional
-----------------------------

The 14 entries above are what the 3 messages requests of the main capture sent
(`claude --print`, text output). All 4 messages requests of the multi-prompt
capture (`claude --print --verbose --input-format stream-json --output-format
stream-json`) sent 15: the same 14 in the same order, with
`thinking-display-updates-2026-08-18` between
`thinking-binding-controls-2026-08-01` and `extended-cache-ttl-2025-04-11`.

Where the 15th comes from, read out of the 2.1.280 bundle on disk
(~/.local/share/claude/versions/2.1.280, 2026-10-20). The 2.1.304 bundle was NOT
inspected, so this paragraph describes 2.1.280:

  - The beta is pushed in one place: the `connector_text` case of a switch over
    the thinking display mode, in the same statement that sets the thinking
    config to `display:"updates"`:

      function wxt(e,n){if(e==="summarized"||e==="highlights")return"thinking_and_connector_text";if(e==="omitted"&&!n)return"none";if(e!=="omitted"&&yQt())return"thinking_and_connector_text";return ldr()?"connector_text":"none"}

    so an `omitted` display (second argument false) is mode `none`, which adds

The three 2.1.304 bodies kept in internal/ccidentity/testdata carry
`"thinking":{"type":"adaptive","display":"omitted"}`; their headers were not

Multi-prompt capture
--------------------

One container process, `claude --print --verbose --input-format stream-json
--output-format stream-json --permission-mode=acceptEdits`, three user messages
written to stdin 12 s apart so each was its own prompt. The third asked for a
Bash `ls -la`. An earlier attempt with no delay between the messages coalesced
the second and third prompts into one request; it is not committed.

  request  cc_turn_index  cc_prompt_index  cc_prompt_id           cc_prev_req
  1        1              0                cc577e4f-… (new)       absent
  2        2              0                8cf9e663-… (new)       present
  3        3              0                4c6ba869-… (new)       present
  4        3              0                4c6ba869-… (same as 3) present

Request 4 is the follow-up after the Bash call and carries
x-claude-code-prev-tool-durations: Bash=22. In every row x-claude-code-prompt-id
equals cc_prompt_id.

What this shows, and what it does not:

  - cc_turn_index counts user prompts from 1. A tool follow-up repeats the
    index of the prompt that triggered it.
  - cc_prompt_id, and with it x-claude-code-prompt-id, is a NEW UUID for every
    user prompt, and repeats only across one prompt's follow-up requests. The
    2.1.280 baseline described it as "stable across the turns of one session";
    its captures held one prompt per process, so they could not show this.
  - cc_prompt_index was 0 in all 7 messages requests of both captures. What
    moves it is `unknown`.
  - Whether cc_turn_index and cc_prompt_id behave the same in an interactive
    session (cc_entrypoint=cli) is `unknown`; every request here is sdk-cli.

Gaps
----

  - The API-key auth mode was NOT captured.
  - The interactive (`cc_entrypoint=cli`) header set was NOT captured. Every
    request is a `--print` or stream-json run, so cc_entrypoint is `sdk-cli`.
  - cch and the cc_version suffix are derived, not opaque. 2.1.304 replaces
    `cch=00000` with the xxHash64 of the body, seed 0x4d659218e32a3268, masked
    to 20 bits, over the body with the first `model` value emptied and the first
    `max_tokens` field removed with one adjacent comma. The suffix is the sha256
    of a salt, three characters of the first prompt and the version. The salt is
    a literal in the 2.1.304 JavaScript; the seed is not in the binary and comes
    from public reverse engineering. Both rules reproduce every body captured
    from 2.1.304 (internal/ccidentity/cch.go; scripts/cc_billing.py computes the
    same).
  - The security-monitor (classifier) request did NOT fire; every messages
    request carried `x-claude-code-request-class: main`.
  - X-Stainless-OS is `Linux` and X-Stainless-Runtime-Version `v26.3.0` because
    the capture ran in a Linux container.
  - The proxy reproduces the per-prompt cc_prompt_id and cc_turn_index from the
    user prompts in each request's own messages (ccidentity.TurnOf), sends
    HTTP/1.1 as every record here shows, and sends cc_prev_req: the request-id
    of the reply the latest assistant message echoes (ccidentity.ReplyLog). That
    is how 2.1.304 derives it, from the requestId of its latest assistant
    message, and it matches every row above: each follow-up names the
    request-id response header of the request before it.
  - cc_prompt_index is 0 in every capture. The 2.1.304 binary adds 1 to it only
    for a prompt whose turn origin is `human` (a prompt a person typed into an
    interactive session). No capture shows that origin: every request here is
    `cc_turn_origin=sdk`. The rule comes from reading the binary, not from a
    capture, and the proxy applies it (ccidentity.BillingHeader: the prompt
    number for a `human` origin, 0 for any other).
  - The 15-entry anthropic-beta of the stream-json run (see "anthropic-beta is
    conditional") is NOT reproduced: the proxy always sends the 14 entries of
    the `--print` text mode, whatever `thinking.display` the caller sent.
