Claude Code 2.1.280 client header baseline (OAuth)
==================================================

> GROUND TRUTH. Every value below is a verbatim quote from intercepted traffic,
> nothing is inferred. Anything not byte-confirmed is marked `unknown`.

Captured:  2026-09-23 (two runs: the first proved the harness, the second was
           taken after the harness was fixed and is the source of the conditional
           header below. Both runs agree on every header listed as static.)
Client:    2.1.280 (Claude Code)
Image:     claude-box:mitm (built from ~/Git/claude-container/Containerfile,
           pin @anthropic-ai/claude-code@2.1.280)
Script:    scripts/capture-claude-code-headers.sh oauth
JSONL:     .reference/claude-code-headers-20260923.jsonl (7 records)
Transport: HTTP/1.1 to api.anthropic.com. NOT HTTP/2. Header case therefore
           reaches the wire as written, so net/http's name canonicalization
           (X-Stainless-OS -> X-Stainless-Os) is a real, not cosmetic, difference.
Auth mode: OAuth only. The API-key header set was NOT captured — see Gaps.

Method
------

Containerized Claude Code, two non-interactive prompts, HTTPS_PROXY pointed at
mitmdump with --allow-hosts restricted to api.anthropic.com. The addon records
headers verbatim and a body fingerprint; request bodies are never dumped.

  scripts/capture-claude-code-headers.sh oauth

Because both prompts ran with `claude --print`, the captured entrypoint is
`sdk-cli`. The interactive entrypoint value is `cli` (recorded independently in
docs/classifier-fallback-notes.md) and was not re-captured here.

Conditional header, absent from the first turn of a session and present after a
tool has run (observed on the third captured request, 2026-09-23 08:48:47Z):

  x-claude-code-prev-tool-durations: Bash=29

Format is `<ToolName>=<milliseconds>`, comma-separated when more than one tool
has run (the multi-tool case is `unknown` — only a single Bash entry was seen).
A session that has never used a tool does not send this header at all, so a
spoof cannot decide it from the request alone; whether the upstream gates on its
absence is `unknown`.

Notably absent: x-api-key. The OAuth path authenticates with Authorization
alone. The proxy currently DELETES Authorization and sets x-api-key for
non-OAuth tokens, and sets only Authorization for OAuth tokens while leaving
x-api-key deleted — which matches this capture for the OAuth case only.

anthropic-beta, verbatim and in order (one comma-separated header value):

  claude-code-20250219,oauth-2025-04-20,interleaved-thinking-2025-05-14,thinking-token-count-2026-05-13,context-management-2025-06-27,prompt-caching-scope-2026-01-05,mid-conversation-system-2026-04-07,advanced-tool-use-2025-11-20,mid-conversation-system-clear-at-2026-08-21,effort-2025-11-24,thinking-binding-controls-2026-08-01,extended-cache-ttl-2025-04-11,cache-diagnosis-2026-04-07

Note the first two entries: `claude-code-20250219` ahead of `oauth-2025-04-20`.
The proxy's ApplyAuthHeaders appends `oauth-2025-04-20` to whatever the client
sent, which cannot produce this ordering.

POST /v1/messages?beta=true — body fingerprint
----------------------------------------------

Top-level keys, all three requests identical:

  context_management, diagnostics, max_tokens, messages, metadata, model,
  output_config, stream, system, thinking, tools

Fields the proxy never produces: `context_management`, `diagnostics`,
`output_config`. Fields routinely produced by clients that Claude Code does NOT
send here: `temperature`, `top_p`, `top_k`, `stop_sequences`, `tool_choice`,
`service_tier`.

Observed scalar values (this session, not constants):

  model: claude-sonnet-5
  max_tokens: 64000
  stream: true
  metadata.user_id: see below

metadata.user_id is NOT the flat `user_<hex>_account_<uuid>_session_<uuid>`
form this plan originally assumed. It is a STRING containing a JSON object:

  "{\"device_id\":\"<64 hex>\",\"account_uuid\":\"\",\"session_id\":\"<uuid>\"}"

account_uuid was empty in every captured request. This was varied on
2026-09-23: a second capture on an independent OAuth credential
(claude-code-headers-20260923-acct2.jsonl, a different Authorization hash) also
sent it empty in all three of its messages requests. Empty in 6 of 6 across two
accounts, so it is general to the OAuth path rather than specific to one token.
The two captures are otherwise identical — running
scripts/diff_claude_code_identity.py with one as baseline and the other as
observed reports no drift across 23 headers, the path, metadata.user_id and
system[0].

  x-anthropic-billing-header: cc_version=2.1.280.5c2; cc_entrypoint=sdk-cli; cch=3d0b8; cc_prompt_id=477866a5-ee79-43d9-8195-509f6420ac11; cc_turn_origin=sdk;

  x-anthropic-billing-header: cc_version=2.1.280.336; cc_entrypoint=sdk-cli; cch=3ab87; cc_prev_req=req_011CfL3J5mtdJ5DhtF1opYTr; cc_prompt_id=518a84e2-4c45-458c-a2f6-363b7ff7fa44; cc_turn_origin=sdk;

Field-by-field:

  cc_version      2.1.280.<3 hex>. The suffix differs BETWEEN PROCESSES
                  (.5c2 vs .336) and is stable within one.
  cc_entrypoint   sdk-cli here; `cli` for interactive sessions.
  cch             5 hex, different on every request. Derivation `unknown`.
  cc_prompt_id    uuid, stable across the turns of one session.
  cc_turn_origin  sdk here; interactive value `unknown`.
  cc_prev_req     present only on a follow-up turn; carries the previous
                  turn's `req_...` id, which is returned in the response.

GET /api/claude_code/* — headers
--------------------------------

  Accept: application/json, text/plain, */*
  User-Agent: claude-code/2.1.280
  Cache-Control: no-cache
  Pragma: no-cache
  Authorization: Bearer <same token>
  anthropic-beta: oauth-2025-04-20
  Accept-Encoding: gzip, compress, deflate, br
  Host: api.anthropic.com
  Connection: close

THIS IS A DIFFERENT USER-AGENT from the messages path. Discovery and policy
calls send `claude-code/2.1.280`; /v1/messages sends
`claude-cli/2.1.280 (external, sdk-cli)`. Two spellings, two families.

Findings that contradict existing repo assumptions
--------------------------------------------------

1. `internal/claudecode/client.go:385` and `:451` send
   `Claude-Code/2.1.246`. The real messages-path value is
   `claude-cli/2.1.280 (external, sdk-cli)` — a different prefix, a different
   case, a version suffix, and a parenthesised mode. Not a version bump.

2. `internal/api/claudecode_proxy.go:142-146` states "Claude Code does not send
   a session header: it carries the identifier in metadata.user_id". The
   capture disproves the first half: `X-Claude-Code-Session-Id` is present,
   stable per process, and is a UUID. metadata.user_id also carries a
   *session_id* and a *device_id*, so the function's body fallback is reading a
   field of a different structure than the comment implies.

3. `internal/claudecode/client.go:48-63` appends `oauth-2025-04-20` to the
   client's beta list. The real list has it second, after
   `claude-code-20250219`. Append-only cannot reproduce the captured order.

4. `docs/classifier-fallback-notes.md` records `cc_entrypoint=cli`. That is the
   interactive value; `--print` sessions send `sdk-cli`. Both are real.

Gaps
----

  - The API-key auth mode was NOT captured. A real Anthropic API key was
     unavailable; the value in the environment was the local proxy's own key.
  - The interactive (`cc_entrypoint=cli`) header set was NOT captured, only the
     `sdk-cli` one. Re-run without `--print` to close this.
  - `cc_turn_origin` for interactive sessions: `unknown`.
  - `cch` derivation: `unknown`. Treated as opaque and generated fresh.
  - The security-monitor (classifier) request did NOT fire. All three messages
     requests carried `x-claude-code-request-class: main`. The Bash-tool prompt
     was accepted rather than approved via a permission prompt, which is the
     likely reason no monitor call was emitted. Recorded, not forced.
  - X-Stainless-OS is `Linux` and X-Stainless-Runtime-Version `v26.3.0` because
     the capture ran in a Linux container. A macOS host's Claude Code would
     report different values. Which to spoof is a decision, not a fact.

Spoofing consequence
--------------------

Reproducing this identity requires, at minimum: the full x-stainless family,
`x-app: cli`, `anthropic-dangerous-direct-browser-access: true`,
`x-claude-code-request-class: main`, `X-Claude-Code-Session-Id`, a
`x-client-request-id`, the 13-entry beta list in captured order, the
`claude-cli/2.1.280 (external, sdk-cli)` User-Agent on the messages path, the
`?beta=true` query string, `Accept-Encoding: gzip, deflate, br, zstd`, and a
system[0] line carrying a fresh `cch` plus a per-session `cc_prompt_id`.
