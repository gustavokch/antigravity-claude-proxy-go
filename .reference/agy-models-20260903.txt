Findings:

1. gemini-3.8 family: NEW upstream (agy CLI account view). Proxy catalog code
   has no 3.8 handling yet — must be added so accounts that publish 3.8
   resolve correctly (aliases, reasoning-effort, tier collapse).
2. gemini-3.5 family: STILL PUBLISHED for the proxy's accounts (View B),
   though absent from the agy CLI account view (View A). NOT dead. Existing
   3.5 aliases stay valid for accounts that receive 3.5.
3. gemini-3.6 medium/low tiers: fluctuate between calls even for the same
   account (View A). Direct IDs resolve whenever upstream publishes them;
   no alias change needed.
4. Tiering shape: upstream publishes per-tier IDs (View A shows
   -high/-medium/-low directly; no "tiered" ID visible in either view).
   applyGemini37's synthetic expansion must not overwrite direct upstream
   tier entries — made shape-agnostic in the code change.
5. Raw fetchAvailableModels JSON: not capturable on this host (cmd/
   cloudcodecheck reads the agy token file at ~/.gemini/antigravity-cli/
   antigravity-oauth-token, which no longer exists for agy 1.1.25; the
   proxy's accounts carry their own credentials). /v1/models public shape
   (View B) is the recorded ground truth instead.

Conclusion:

  Catalog support is added as a pure superset: add gemini-3.8 handling;
  keep every existing family that any account still publishes. Model
  availability differences between accounts are upstream behavior, not a
  proxy defect.
